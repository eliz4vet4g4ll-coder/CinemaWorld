# Контракт API для фронтенда

Основа — фрейм «Data & REST API» в Figma (рабочий файл: «CinemaWorld · MVP & Prototype (Copy)»). Ниже то, что фронтенд ожидает от бэкенда: макет задаёт список операций
и сущности, а раздел «Что добавлено к макету» нужно согласовать.

Формат — JSON. Базовый адрес задаётся в `VITE_API_URL`. Даты — ISO 8601 с часовым поясом, цена — число в рублях.

## Операции

| Метод и путь | Доступ | Ответ | Ошибки |
|---|---|---|---|
| `GET /movies` | все | `Movie[]` | |
| `GET /movies/{id}` | все | `Movie` | 404 |
| `GET /sessions?movieId=&date=YYYY-MM-DD` | все | `Session[]` без прошедших сеансов | 400 |
| `GET /sessions/{id}/seats` | все | `Seat[]` | 404 |
| `POST /tickets` `{sessionId, seatId}` | пользователь | 201 `Ticket` | 400, 401, 404, **409 место занято** |
| `GET /tickets/{id}` | владелец, админ | `Ticket` | 401, 403, 404 |
| `POST /auth/login` `{email, password}` | все | `{token, user}` | 401 |
| `POST /auth/register` `{name, birthDate, email, password}` | все | 201 `{token, user}` | 400, **409 email занят** |
| `GET /me` | пользователь | `User` | 401 |
| `GET /me/tickets` | пользователь | `Ticket[]` | 401 |
| `GET /admin/{movies,cinemas,halls,sessions}` | админ | список | 401, 403 |
| `POST /admin/{ресурс}` | админ | 201, запись | 400, 401, 403 |
| `PATCH /admin/{ресурс}/{id}` | админ | запись | 400, 401, 403, 404, 409 для зала с сеансами |

## Модели

```ts
Movie   { id, title, description, poster, duration, ageRating, year, genre, director, cast, backdrop?, tagline? }
Cinema  { id, name, address }
Hall    { id, cinemaId, name, category, seatCount, rowCount, hasActiveSessions }
Session { id, movieId, cinemaId, hallId, startsAt, ticketPrice, cinema: Cinema }
Seat    { id, hallId, row, number, occupied: boolean }
Ticket  { id, number, userId, sessionId, seatId, status: "issued", createdAt, movie: Movie, session: Session, seat: {row, number} }
User    { id, name, email, role: "user" | "admin" }
```

Формат ошибки: `{ "message": "текст", "errors": { "поле": "текст" } }`. `errors` нужен только при 400:
фронтенд покажет эти тексты у полей формы.

## Что добавлено к макету: нужно согласовать

1. **`Session.cinema`.** Экраны сеансов показывают название и адрес, а `/cinemas` для посетителя нет. Иначе нужен отдельный публичный запрос.
2. **`Seat.occupied`.** В сущности «Место» занятости нет, она зависит от сеанса, поэтому поле вычисляется в ответе `/sessions/{id}/seats`.
3. **`Ticket`** возвращается с вложенными `movie`, `session`, `seat`, плюс `number` для показа («CW-2026-0148»).
4. **Заголовок `Idempotency-Key` в `POST /tickets`.** Правило макета: «Один запрос не создаёт два билета». Повтор с тем же ключом должен вернуть уже созданный билет. Уникальный индекс в БД на пару `(sessionId, seatId)` при этом всё равно нужен: он и даёт 409.
5. **Вход:** `Authorization: Bearer <token>`. `User.role` приходит названием роли, а не `roleId`. Если выберете cookie-сессии, меняется только `src/api/client.ts`. `POST /auth/logout` в макете нет, выход сейчас только удаляет токен в браузере.
6. **`AdminSession` = `Session` + `movieTitle`** для таблицы сеансов.
7. **`Movie.backdrop`, `Movie.tagline`** необязательны: широкий кадр и короткий текст для hero, без них берутся `poster` и `description`.
8. **Постер** отправляется строкой data URL (до 2 МБ) в поле `poster`, а отдаётся как URL. Отдельной загрузки файлов в контракте нет; если сделаете её, поменяется только форма фильма.
9. **Поиск и фильтры каталога** работают в браузере поверх `GET /movies`. Если фильмов станет много, понадобятся параметры запроса.
10. **Удаления записей (`DELETE`) в макете нет**, поэтому в админке его тоже нет.

## Залы и регистрация: появились в макете, но не в его фрейме «Data & REST API»

11. **Новая сущность «Зал»** и ресурс `/admin/halls`. Сеанс получает `hallId`, а место относится к залу, а не к кинотеатру (`Seat.hallId` вместо `Seat.cinemaId`). Это меняет схему БД.
12. **Сервер проверяет, что зал принадлежит выбранному кинотеатру сеанса**, и при ошибке возвращает 400 с `errors.hallId`.
13. **Места зала создаёт сервер.** В форме задаются только `seatCount` и `rowCount`, поэтому ряды считаются одинаковыми, а `seatCount` должен делиться на `rowCount` без остатка: 240 мест на 8 рядов дают по 30 мест. Иначе 400 с `errors.seatCount`.
14. **Решено с Александром: зал с сеансами редактировать нельзя.** `GET /admin/halls` возвращает вычисляемое поле `hasActiveSessions`, а `PATCH /admin/halls/{id}` в таком случае отвечает **409** с `message`. Фронтенд считает активным сеанс, который идёт или ещё не начался (конец = `startsAt` + длительность фильма); нужно подтвердить это правило на бэкенде.
15. **`POST /auth/register`.** `birthDate` в формате `YYYY-MM-DD`, пароль от 8 символов (хранить только хеш), email без учёта регистра. Роль всегда `user`, клиент её не передаёт. В сущности «Пользователь» появляется `birthDate`.
16. Категории зала на фронтенде: `2D`, `3D`, `IMAX`. В макете показана только `2D`, список нужно согласовать.
17. **Решено с Александром: вход один для всех.** `POST /auth/login` принимает email и пароль любого пользователя и возвращает `user.role`, по которой фронтенд открывает кабинет или админку. Отдельного входа для администраторов нет: сотрудники входят с рабочей почты, роль назначает сервер. `POST /auth/register` всегда создаёт роль `user`, в том числе для адресов на рабочем домене. Проверка прав на `/admin/*` по-прежнему обязательна на сервере.
